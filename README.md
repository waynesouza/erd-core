# ERD Core

This is a Java-based project that uses Spring Boot and Maven. The project is designed to manage diagrams related to a project.

## Getting Started

These instructions will get you a copy of the project up and running on your local machine for development and testing purposes.

## Running with Docker

This is the recommended way to run the full stack locally. The `docker-compose.yml` in this repository orchestrates all services: PostgreSQL, MongoDB, the backend (erd-core), and the frontend (erd-client).

1. **Start all services** from the `erd-core/` directory:

```bash
docker compose up --build
```

> The first build takes several minutes as Maven downloads all dependencies. Subsequent runs are faster thanks to the cached Maven volume.

### Useful commands

```bash
# Run in background
docker compose up -d

# View logs for a specific service
docker compose logs -f erd-core

# Stop all services
docker compose down

# Stop and remove all volumes (resets database data)
docker compose down -v

# Rebuild a specific service
docker compose up --build erd-core
```

## Running Locally (without Docker)

### Prerequisites

- Java 17
- Maven
- Spring Boot
- PostgreSQL and MongoDB running locally (use `docker-compose-local.yml` to spin up only the databases)

### Start only the databases

```bash
docker compose -f docker-compose-local.yml up -d
```

Then run the application:

```bash
mvn spring-boot:run
```

## Deploy (Render + Neon + MongoDB Atlas)

The stack runs entirely on free tiers: two Render web services built from the Dockerfiles, a Neon
PostgreSQL database and a MongoDB Atlas free cluster. Each repository carries its own Blueprint
(`render.yaml`): this one declares `erd-core`, and erd-client declares the frontend. Render forbids
a resource from belonging to two Blueprints, and keeping them apart also keeps each repository's
deploy records on its own GitHub Deployments tab.

The browser only ever talks to `erd-client`, which proxies `/api` and `/ws` to `erd-core`. Staying
on a single origin matters: `onrender.com` is on the Public Suffix List, so two sibling subdomains
count as different sites and the JWT cookie would never be sent.

### 1. Databases

- **Neon** (AWS us-east-1): create the `diagram` database and copy the **direct** host, the one
  without `-pooler`, because Hibernate runs DDL on startup.
- **Atlas** (free cluster, AWS us-east-1): create a user with `readWrite` on a database named
  `erd`. Atlas reserves `local`, which is the name used for local development. Under Network
  Access, allow Render's outbound IPs (service page → Connect → Outbound).

### 2. Blueprint

In Render, choose **New → Blueprint** and pick this repository. Render reads `render.yaml`, creates
the service and asks for the four values that are not in the file (see section 3). Repeat the step
in the erd-client repository to create the frontend service.

A Blueprint never adopts an existing service: if one with the same name is already in the
workspace, Render appends a suffix and the URL changes. When that happens, update `BACKEND_URL`
(erd-client) and `ERD_APP_WEBSOCKET_ALLOWED_ORIGINS` (erd-core) with the real URLs and redeploy.

### 3. Environment variables

Anything in `application.yml` can be replaced by an environment variable, because Spring's relaxed
binding maps `erd.app.jwt.secret` to `ERD_APP_JWT_SECRET` and gives the variable precedence. That
is why no production credential lives in the repository.

#### Asked by Render on the first deploy (`sync: false`)

These are the secrets. Render stores them encrypted and never writes them to git.

| Variable | Value |
| --- | --- |
| `SPRING_DATASOURCE_URL` | `jdbc:postgresql://<neon-host>/diagram?sslmode=require` — the **direct** host, without `-pooler`. Drop `channel_binding`, which is libpq syntax the JDBC driver does not understand. |
| `SPRING_DATASOURCE_USERNAME` | Neon user, e.g. `neondb_owner` |
| `SPRING_DATASOURCE_PASSWORD` | Neon password |
| `SPRING_DATA_MONGODB_URI` | `mongodb+srv://<user>:<password>@<cluster>.mongodb.net/erd?retryWrites=true&w=majority&authSource=admin` |

`authSource=admin` is not optional: naming a database in the URI path makes the driver authenticate
against that database, and Atlas keeps its users in `admin`. Passwords containing `$ : / ? # [ ] @`
must be percent-encoded.

#### Already declared in `render.yaml`

Nothing to type: they exist so the service fits the free instance and talks to the right frontend.

| Variable | Value | Why |
| --- | --- | --- |
| `PORT` | `8080` | Port Render routes traffic to |
| `JAVA_TOOL_OPTIONS` | `-XX:MaxRAMPercentage=75 -XX:+UseSerialGC -XX:TieredStopAtLevel=1 -Xss512k` | Keeps heap and JIT within 512 MB / 0.1 CPU |
| `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE` | `3` | Neon's free compute is small |
| `SPRING_JPA_SHOW_SQL` | `false` | Keeps the logs readable |
| `ERD_APP_JWT_SECRET` | generated by Render | Random base64 256-bit value, which is what `JwtService#getKey` expects. The secret in `application.yml` stays local-only. |
| `ERD_APP_JWT_COOKIE_SECURE` | `true` | Marks the JWT cookies `Secure`, since Render serves HTTPS |
| `ERD_APP_WEBSOCKET_ALLOWED_ORIGINS` | `https://erd-client.onrender.com` | Origin the STOMP handshake arrives with. A mismatch — a trailing slash, `http` instead of `https`, a suffixed service name — answers `403` and breaks real-time collaboration. |

#### Optional overrides

Defined in `application.yml` with working defaults; set them only to change behaviour.

| Variable | Default | Meaning |
| --- | --- | --- |
| `ERD_APP_JWT_EXPIRATION` | `3600000` | Access token lifetime, in ms (1 h) |
| `ERD_APP_JWT_REFRESH_EXPIRATION` | `2629746000` | Refresh token lifetime, in ms (~30 days) |
| `ERD_APP_JWT_COOKIE_NAME` | `erd-token` | Access token cookie name |
| `ERD_APP_JWT_REFRESH_COOKIE_NAME` | `erd-refresh-token` | Refresh token cookie name |
| `SPRING_JPA_HIBERNATE_DDL_AUTO` | `update` | Schema strategy on startup |

#### Local development (`.env`)

`docker-compose.yml` reads `.env`, which is gitignored; `.env.example` lists every key with
working values, so copying it is enough to run the stack.

| Variable | Used for |
| --- | --- |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, `POSTGRES_PORT` | The local Postgres container and the JDBC URL built for the app |
| `MONGO_ROOT_USERNAME`, `MONGO_ROOT_PASSWORD`, `MONGO_DB`, `MONGO_PORT` | The local MongoDB container and its URI |
| `SPRING_LOCAL_PORT`, `SPRING_DOCKER_PORT` | Host and container ports of the backend |
| `CLIENT_LOCAL_PORT`, `CLIENT_DOCKER_PORT` | Host and container ports of the frontend |
| `JWT_SECRET`, `JWT_EXPIRATION`, `JWT_REFRESH_EXPIRATION`, `JWT_COOKIE_NAME`, `JWT_REFRESH_COOKIE_NAME` | JWT settings passed to the app |

One catch: compose passes these to the app through `SPRING_APPLICATION_JSON`, which outranks plain
environment variables in Spring's precedence order. To point the local stack at a remote database,
edit that JSON in `docker-compose.yml` — setting `SPRING_DATASOURCE_URL` alongside it has no effect.

### 4. Continuous deployment

Both Blueprints use `autoDeployTrigger: checksPass`, so merging a pull request into `main` deploys
only once the merge commit's checks are green. Render skips the deploy entirely when a commit
carries no checks, which is why `tests.yml` here — and `build.yml` in erd-client — also run on
pushes to `main`, and not only on pull requests.

### 5. What the free tier implies

- Services sleep after 15 minutes without traffic and take around a minute to wake up. In-memory
  state — entity locks and the STOMP simple broker — is lost when that happens.
- The 750 free instance hours per month are shared by both services, so keeping them awake around
  the clock with an external pinger would exhaust the quota.
